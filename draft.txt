Bài toán
Hệ thống phân phối nhạc tới các DSP (Spotify, Apple Music, TikTok...). Một release có nhiều tracks. User submit release, chọn DSP muốn đẩy lên — hệ thống sinh ra pipeline xử lý phức tạp gồm nhiều step tuần tự/song song, có thể retry, cancel, chờ đối tác.

Data model
release
  id, title, artist_id, ...

track
  id, release_id, title, duration, ...

dsp
  id, name (spotify | apple_music | tiktok...)

── Mỗi lần user bấm submit ──────────────────────────────

release_submission
  id
  release_id
  type: delivery | takedown
  dsp_ids: int[]          ← user chọn DSP nào
  submitted_by, submitted_at

── Pipeline orchestration ───────────────────────────────

pipeline_execution
  id
  submission_id           ← trỏ release_submission (nguồn gốc của pipeline)
  parent_execution_id     ← null nếu root, self-join thành cây
  step_type               ← validate | gen_upc | gen_isrc | create_ern | upload_sftp | poll_partner...
  execution_mode          ← sequential | parallel
  failure_policy          ← stop_all | isolate
  status                  ← StepStatus
  input: jsonb
  output: jsonb
  attempt_number, max_attempts
  started_at, finished_at

pipeline_step_log
  id, execution_id
  level: info | warn | error
  message, metadata: jsonb
  created_at

── Kết quả cuối cùng (chỉ ghi khi pipeline thành công) ──







release_dsp_delivery
  id, release_id, dsp_id
  status: ReleaseDspStatus  ← never_distributed | distributed | taken_down...
  context: jsonb            ← upc, isrcs (shared data sau khi gen xong)
  last_submission_id        ← trỏ lần submit gần nhất thành công
Quan hệ:
release (1) ──< track (nhiều)
release (1) ──< release_submission (nhiều)   ← mỗi lần submit/takedown
release_submission (1) ──< pipeline_execution (nhiều, cây)
release (1) ──< release_dsp_delivery (nhiều) ← 1 row per DSP, upsert khi done

Status 3 tầng
StepStatus (internal)
  pending | running | success | failed
  retrying | waiting_input | cancelled | skipped

ReleaseDspStatus (user thấy, per DSP)
  never_distributed | distributed | taken_down | cancelled | processing | issues

ReleaseStatus (user thấy, tổng release)
  draft | submitted | processing | distributed | failed | taken_down | cancelled
Rollup rules — pure function, không side effect:
typescript// StepStatus[] → ReleaseDspStatus
function rollupDspStatus(statuses: StepStatus[]): ReleaseDspStatus {
  if (statuses.some(s => ['running','retrying','waiting_input'].includes(s)))
    return 'processing';
  if (statuses.every(s => s === 'success'))
    return 'distributed';
  if (statuses.some(s => s === 'failed') && statuses.some(s => s === 'success'))
    return 'issues';
  if (statuses.some(s => s === 'failed'))
    return 'never_distributed';
  if (statuses.every(s => ['cancelled','skipped'].includes(s)))
    return 'cancelled';
  return 'processing';
}

// ReleaseDspStatus[] → ReleaseStatus
function rollupReleaseStatus(statuses: ReleaseDspStatus[]): ReleaseStatus {
  if (statuses.some(s => s === 'processing'))     return 'processing';
  if (statuses.every(s => s === 'distributed'))   return 'distributed';
  if (statuses.every(s => s === 'cancelled'))     return 'cancelled';
  if (statuses.some(s => s === 'distributed'))    return 'failed'; // có DSP ok, có DSP fail
  return 'failed';
}

Kiến trúc xử lý
POST /release/:id/submit { dsps, type }
  → tạo release_submission
  → tạo cây pipeline_execution trong DB
  → queue.add('run_pipeline', { submissionId })
  → return 202

BullMQ worker
  → PipelineEngine.run(submissionId)
  → executeNode(root, abortSignal)

executeNode(node):
  sequential → chạy lần lượt
               nếu fail + stop_all → cancel siblings (SKIPPED)
  parallel   → Promise.allSettled()
               isolate: DSP này fail không ảnh hưởng DSP khác
  leaf node  → StepRegistry.get(stepType).execute(input, signal)
  sau mỗi node → rollupStatus() đệ quy lên parent → lên root
               → upsert release_dsp_delivery nếu là DSP step
Cây pipeline sinh ra khi submit:
root (sequential)
  ├── validate
  ├── gen_upc
  ├── gen_isrc
  └── dsp_group (parallel)
        ├── spotify_pipeline (sequential)
        │     ├── create_ern
        │     ├── upload_sftp
        │     └── poll_partner
        ├── apple_pipeline (sequential)
        │     └── ...
        └── tiktok_pipeline (sequential)
              └── ...

Cancel
User cancel:
  cancelSubtree(rootId, abortController)
  → abort signal → handler đang chạy tự cleanup (đóng SFTP, rollback...)
  → RUNNING → CANCELLED
  → PENDING | RETRYING → CANCELLED
  → SUCCESS | FAILED → giữ nguyên
  → rollup → release_dsp_delivery.status = cancelled

System cancel (stop_all khi sibling fail):
  → chỉ cancel cùng cấp, không đụng parent hay branch khác
  → PENDING → SKIPPED (phân biệt với user cancel)
  → RUNNING → CANCELLED



Retry
Auto retry (trong handler):
  attempt_number < max_attempts → tự retry, status = retrying

Manual retry (qua API):
  PATCH /execution/:id/retry { input? }  ← có thể update input trước khi retry
  → update input trong DB
  → queue.add('retry_step', { executionId })
  → chạy lại từ step đó, không chạy lại cả pipeline

Những điểm quan trọng khi implement
rollupStatus phải pure function — không DB write, không side effect, chỉ nhận list status trả ra status mới. Sai chỗ này là sai toàn bộ data hiển thị.
AbortSignal phải truyền xuyên suốt từ engine xuống handler. Handler tự đăng ký signal.addEventListener('abort', cleanup) — không cleanup là để lại rác trên SFTP, email gửi dở, data không nhất quán với DSP.
context trong release_dsp_delivery là single source of truth cho UPC và ISRCs. Gen xong lưu vào đây ngay, các step sau đọc từ context, không truyền qua nhau qua output.
release_dsp_delivery chỉ upsert khi pipeline thành công — đây là bảng trạng thái thuần, không phải bảng orchestration. Nguồn gốc orchestration là release_submission.
